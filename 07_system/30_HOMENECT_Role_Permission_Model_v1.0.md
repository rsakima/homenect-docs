# HOMENECT 役割・権限モデル 正式決定

**Version:** v1.0  
**基準日:** 2026-09-16  
**Status:** LOCKED / FORMAL DECISION / P0実装対象  
**適用範囲:** Customer / Partner / HOMENECT運営の認証・認可・画面表示・API・RLS・監査

## 1. 正式採用する利用者区分

HOMENECTの利用者は、利用者に分かりやすい単位として次の**3グループ**に整理する。

1. **お客様**
2. **協力業者**
3. **HOMENECT運営**

システム内部では、上記3グループを次の**7役割**で権限制御する。

| グループ | 日本語表示名 | 内部コード | 主な責務 |
|---|---|---|---|
| お客様 | お客様 | `customer` | 自分の予約・機器・承認・確認 |
| 協力業者 | 協力業者管理者 | `partner_admin` | 自社の案件・スタッフ・予定・対応範囲の管理 |
| 協力業者 | 作業スタッフ | `technician` | 割当案件の施工・記録・現場報告 |
| HOMENECT運営 | 運営管理者 | `ops_admin` | 予約・割当・HELP・Referral・日常運営 |
| HOMENECT運営 | 経理管理者 | `finance_admin` | 売上・報酬・手数料・精算・補填 |
| HOMENECT運営 | 事故・コンプライアンス管理者 | `compliance_admin` | 事故・苦情・違反調査・証拠・対応履歴 |
| HOMENECT運営 | 最高管理者 | `super_admin` | 権限・重要設定・緊急例外操作 |

## 2. 共通ルール

- **1人1アカウント**を原則とする。同じ人物の役割ごとの別アカウント作成を前提としない。
- **1人が複数役割を兼任できる。** 例：1人親方は `partner_admin + technician` を同時に保持できる。
- Partner側の役割は**所属Partner単位**で付与する。役割は人物そのものではなく「誰が、どの組織で、何をできるか」として管理する。
- HOMENECT運営側も初期は兼任可能とし、組織拡大後に役割分離できる。
- 認可は**deny-by-default（原則禁止）**とし、明示的に許可された操作のみ実行できる。
- RLSだけに依存せず、Server API / Use Case層でも権限・所属・案件割当を再検証する。
- 重要操作は `actor / role / organization / action / target / reason / timestamp` を監査ログへ記録する。
- 最高管理者は通常業務用ではなく、権限管理・重要設定・緊急例外のための最上位権限とする。

### 条件付き権限の補足

- `technician` のJob Offer受諾・辞退は、Partner設定で許可され、かつ本人に提示された案件に限定する。許可しないPartnerでは `partner_admin` が受諾・辞退する。
- `partner_admin` が実作業を行う場合は、同一アカウントへ `technician` 役割も付与する。管理者権限だけで現場作業権限を暗黙付与しない。
- PIIは案件受諾前に最小化し、受諾・割当後も業務上必要な範囲のみ表示する。
- `super_admin` が通常業務を代行する場合は、理由入力とAuditを必須とする。

## 4. 自己承認を禁止する高リスク操作

兼任自体は許可するが、次の高リスク操作は**起案者と最終承認者を同一人物にしない**ことを原則とする。

1. HOMENECT負担の補填・特別支払の最終承認
2. Configや通常フローを上書きする強制価格変更
3. 設定閾値を超える重大返金・特別対応
4. 自分自身への運営権限昇格、特に `super_admin` 付与
5. Partnerの長期停止・契約終了等の重大Compliance処分
6. 監査・PII保護を弱める重要セキュリティ設定変更

ただしCustomer本人による追加作業・追加料金の承認は「自己承認」ではなく正式なCustomer承認フローであり、本ルールの対象外とする。

**例外:** Pilot初期等で物理的に承認者を2名確保できない場合は、対象操作を実行不可にせず、`reason + audit + 後日レビュー` を必須とする。Productionまでに対象操作ごとの二者承認要否をConfig/Policyとして確定する。

## 5. 役割ではない業務上の立場

次はログイン権限のロールではない。

- 優先業者（Preferred Partner）
- 予備業者（Backup Partner）
- 応援業者（HELP Partner）
- 専門業者（Specialist Partner）

同一Partnerが案件ごとに異なる立場を持つため、RBACロールではなくPartner関係・案件属性として管理する。

## 6. 実装要件

- 人物/認証主体とロールを分離する。
- Partnerロールには `partner_id` 等のorganization scopeを必須とする。
- 1ユーザーに複数ロールを付与できる中間関係を持つ。
- UIの表示/非表示だけでなく、API・Use Case・RLSで同じ権限制御を強制する。
- Role変更、重要PII閲覧、価格・補填・Compliance・緊急例外操作はAudit対象とする。
- 監査ログはappend-onlyとし、通常ロール・最高管理者とも削除・改変不可とする。
- 権限テストでcross-customer / cross-partner / unauthorized-admin操作を拒否できることを受入基準とする。

## 7. 正式決定

HOMENECT P0の利用者・権限モデルとして、**3グループ・7役割 + 複数役割兼任 + 組織スコープ + deny-by-default + 高リスク自己承認禁止 + Audit** を正式採用する。

本Decisionは既存のCustomer / Partner Owner/Admin / Technician / HOMENECT AdminというActor定義を具体化するものであり、既存の価格保護、HELP、Referral、PII、Incident、Complianceの正式ルールを変更しない。
